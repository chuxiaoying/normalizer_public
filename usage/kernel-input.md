# 准备 CLI 输入

给 Normalizer 的是一个**分析工程根目录**，不是生产工作区的任意上级目录。只放分析入口所需的纯净源码，以及源码使用的类型和显式合同，保留相对路径。框架原件、预处理对照和预期 PERS 都在分析工程外。

| 原始材料 | 准备好的输入 | 下一步 |
|---|---|---|
| 已符合设计的 Java | 可达逻辑由源码或明确合同交代，计算边界可证明；入口是可定位的静态方法或静态可达的接收者调用 | `source` |
| JavaScript / TypeScript | 闭合的严格 `.ts` 源码和适配器可定位的导出入口，可含受支持的项目相对导入，见[CLI 当前实现限制](cli.md#当前实现限制) | `module` |
| Vue、小程序等前端业务入口 | 从原工程取证并预处理；只交付符合设计和当前适配限制的纯净 TypeScript。原始模板不进入运行工程 | `scenario`，选择 VO 生产或消费 |

生产框架的配置可用来找出实际装配，但不能原封不动交给 CLI 来完成装配；应把确认会生效的逻辑写进分析副本。交付前先按[设计校验](../design/chapters/04-AI救赎.md#ai-11-分析副本先通过静态校验)检查，再核对[当前实现限制](cli.md#当前实现限制)。前者不满足要补证据，后者不能无损适配就报告工具缺口。

入口统一写作 `工程相对路径#入口调用`，不附带某次调用的实际参数。准备时先核对可见源码、边界、状态和类型；需要修改时查[场景入口及预处理指引](../design/chapters/09-场景归一.md#规则区)。分析副本缺少关键证据时，说明缺口后停止，不用占位值换取运行成功。

命令和约束见 [CLI](cli.md)。`normalizer.kernel-input/1` 是适配器内部交接协议，不是第四种公开输入，CLI 使用者不需要手写；维护者查[实现区](../implementation/contracts/normalized-source-contract.md)。

## 按页面查找和交付入口

按[已选方向和范围](skills/normalizer-preprocess/SKILL.md#前端整页归一化)准备输入。选局部就定位那个绑定；选整页则从路由、页面注册和模板展开实际挂载的子组件、条件分支、列表和插槽。自有组件沿源码继续查，第三方组件按实际接入的属性、事件和公开合同核对。记下每个使用点所属的实例和源位置。

- **查生产入口。** 从页面和组件的注册点找生命周期、模板事件、定时或订阅回调，沿框架转发找到实际接手的 handler。跟到原入口完成，核对等待、失败及清理；原入口已返回而异步任务仍继续时，另追后续触发的回调。
- **查消费入口。** 从实际文本、展示和交互属性回查父级供值、缺省值及挂载条件。列表里同一模板用于多行时，保留行的身份和范围。弹窗未挂载与已挂载但属性值为空，要按原件分别核对。
- **认回同一份 VO。** 从一次写入向后找读点，也从模板或请求实参向前找持有者。沿别名找到原字段，核对初始化、替换、合并、重置和实际取值。父组件只透传账单时沿用原值；若另存了提交快照，就跟踪那份快照。动态键缺少依据时记下未能定位的范围。[场景预处理规则](../design/chapters/09-场景归一.md#规则区)

按“源位置和绑定 → 分析入口 → 实跑 PERS 或具体诊断”核对已选范围。同一可复用入口的多个绑定都要能找回。保留可复跑的分析输入和命令，需要审查改写时提供带上下文的 diff。从原件独立核对输入、状态、调用、完成及失败；逐项标明已核实、被拒绝或缺证据。整页任务只有在所选方向的应查项都已核实后才报完成。[CLI 诊断](cli.md#诊断) · [结果验收](../design/chapters/08-统一定形.md#cf-06-完整-pers-验收)

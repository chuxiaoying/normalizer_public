# 作为用户与 Normalizer 之间的代理人

如果你是一个 agent，从读到这里开始，你就是用户与 Normalizer 之间的代理人。用户告诉你想弄明白什么，你负责听懂这句话，找到能回答它的源码和入口，用 Normalizer 得到结果，再用用户原来的业务词汇回答。用户可以一直说「欠费单」「查账」「还款按钮」，由你来判断何时需要谈 handler、VO 或 PERS。

**先听问题，再选工具。** 用户要读懂已有结果，就用已有结果解释。要分析源码，就先看用户给的工程。能从代码查到的绑定自己查；只有几种合理理解会让分析不同的入口、给出不同的答案时，才拿具体选项和用户商量。下面是一些从简单到复杂的说法。

### 「帮我看看，加一这个函数会返回什么？」

如果用户指的是入门例子里的 `HelloWorld.addOne(int value)`，入口和问题都已明确。直接从 Java 源码运行 `source`，读出 R，再答「传进什么数，就返回那个数加一」。用户问的是规律，无须先问他打算传几。若他说「我想自己试跑一遍」，就带他走可复制的入门例子。[可运行的加一例子](../../getting-started.md#1-java从源码直接得到-pers)

### 「这份结果里为什么既有扣库存，又有一个订单号？」

用户已经给了 PERS，先就这份结果回答。拿设计里的创单例子来说，S 写明先扣库存、再发起创单，R 说明成功时返回这次创单得到的订单号。用户要的是读懂业务效果，到这里就能回答；如果他进一步问「源码真是这样吗」，再回到原入口核对。[库存与创单的完整 PERS](../../../design/chapters/07-PERS登场.md)

### 「帮我看看这个报价接口，线上到底按哪套价格算？」

「报价接口」指向 Java 服务入口，「线上哪套」提示你查生效的装配配置。先从 HTTP 或 RPC 绑定找到服务方法，再追到实际注入的计价实现。源码和配置已经给出答案，就按第九章准备该入口并运行 `source`。若工程同时提供零售和批发两套配置，却缺少目标部署的选择依据，就问「你要看哪个部署环境的报价？」最后用核实的计价实现和返回公式回答。[Java 服务端允许改什么](../../../design/chapters/09-场景归一.md#java-服务端允许改什么) · [准备 CLI 输入](../../kernel-input.md)

### 「我只想知道，这张欠费单上的还款按钮什么时候能点。」

「只看这个按钮」已经限定范围，「什么时候能点」指向它的可用性属性，做一次前端消费即可。找到实际按钮的属性绑定，按第九章准备取值函数并运行消费场景。用分析得到的条件回答「哪些情况下可点」。如果代码还表明按钮只在弹窗打开时出现，把「什么时候出现」和「出现以后什么时候可点」说清楚。[前端消费允许改什么](../../../design/chapters/09-场景归一.md#前端消费允许改什么) · [前端场景命令](../../cli.md#前端-vo-场景)

### 「点还款以后，会发什么请求？失败了页面会怎样？」

还是那个按钮，这次用户问的是点击发生**以后**的事。做前端生产，从模板实际绑定的点击 handler 开始，沿着调用查请求、失败处理和页面状态写入。运行生产场景后，用它的结果回答什么条件下会发请求、失败时页面做了什么。如果用户还想知道错误提示具体显示哪句话，再加上那条提示的消费入口。两次观察可以沿同一份页面状态对起来。[前端生产允许改什么](../../../design/chapters/09-场景归一.md#前端生产允许改什么) · [前端场景命令](../../cli.md#前端-vo-场景)

## 前端整页归一化

### 「把这张欠费单页面归一化。」

页面已给，方向和范围还可能有几种理解。先看页面实际有哪些绑定，再用页面里的词和用户商量。例如查到查询、还款和金额展示，可以问：「你关心点查询、点还款以后会发生什么，还是金额怎样显示、按钮什么时候能点？可以两边都看。你想看其中几项，还是所选方向的整页？」

- 用户答「只看点查询」，就分析那个生产入口。
- 用户答「整页生产」，就找全这页实际的业务回调，包括页面加载和子组件转交的事件。用户一开始已这样说，直接做。
- 用户答「生产和消费都要，整页」，就按页面装配分别找全回调和属性，逐入口运行相应的场景命令。按两侧分别交代已完成的范围和具体缺口。[页面入口的查找与交付](../../kernel-input.md#按页面查找和交付入口)

### 「只跑通了金额卡片。那我能说这页都归一化了吗？」

先看实际运行了什么。若只有金额属性得到了消费 PERS，就答「目前能解释金额怎么显示」。如果用户原先选了整页，就接着做其余已选入口；若某个生产入口被 CLI 拒绝，给出对应源码位置、诊断和受影响的业务问题。若发现副本删去了用户关心的请求，就向用户说明这份结果回答不了原问题，并按设计修正副本。按诊断区分需要补的原工程资料和当前工具缺口，继续处理能独立完成的入口。[CLI 诊断](../../cli.md#诊断) · [预处理允许改到哪里](../../../design/chapters/04-AI救赎.md#ai-05-预处理停在哪儿) · [业务行为被删去的判例](../../../design/chapters/06-业务至上.md#bf-01-省略的两个前提)

**范围谈清之后就动手。** 普通 Java 函数或独立 TypeScript 模块按输入手册选 `source` 或 `module`；涉及服务或页面时，从第九章对应场景进入需要的 AI 预处理规则，准备分析副本，再按 CLI 手册实际运行。用户要验收时，从原源码独立核对完整结果。交付时先回答用户起初的业务问题，再给可复核的入口、PERS 或诊断。[输入清单](../../kernel-input.md) · [第九章《场景归一》](../../../design/chapters/09-场景归一.md#规则区) · [CLI 手册](../../cli.md) · [第七章《PERS登场》](../../../design/chapters/07-PERS登场.md) · [完整 PERS 验收](../../../design/chapters/08-统一定形.md#cf-06-完整-pers-验收)

# Normalizer

Normalizer 从选定的业务入口归一化参数、返回值、状态、外部调用和异常，输出 PERS。

- **定规则**：[设计区](design/README.md)。章节及规则区裁决语义。
- **跑程序**：[使用区](usage/README.md)。准备输入、选择 CLI 入口、查看诊断。
- **改代码**：[实现区](implementation/README.md)。查看模块、接口、维护和发布入口。
- **验收**：[测试区](tests/README.md)。管理测试种子，用派生的完整工程核对真实 CLI 输出。

开发前先读[仓库指引](AGENTS.md)。

## 维护守则

### 四个工作区

| 目录 | 负责回答 | 怎么组织 |
|---|---|---|
| [`design/`](design/README.md) | 系统应该做什么、何时拒绝、输出怎样才唯一 | `chapters/` 的各章及其规则区是唯一裁决依据；目录页只导航。 |
| [`implementation/`](implementation/README.md) | 规则怎样落到代码，出错在哪一层查 | `packages/` 放内核，`tools/` 放 CLI 和适配工具，`apps/` 放阅览器等应用。`contracts/` 放机器接口、内部交接与交付约束；`docs/` 放维护者的接线、定位、构建与诊断说明。 |
| [`tests/`](tests/README.md) | 怎样证明正式 CLI 符合设计 | [`seeds/`](tests/seeds/README.md) 放语义例证和种子清单，按基础主题或联合主题归档。`e2e/catalog.yaml` 按种子 ID 登记 CLI 入口；`e2e/cases/` [沿用种子的主题路径](tests/README.md#登记及文件布局)，每个种子下按入口、原例和变体展开：`src/` 存完整分析工程，`case.yaml` 存入口和一份独立推导的完整 PERS 或拒绝断言。测试不另定主题归属。 |
| [`usage/`](usage/README.md) | 使用者怎么准备输入、运行和处理失败 | 入门示例负责从零跑通；命令、参数、场景与诊断集中到 CLI 参考。`skills/` 放人或 agent 调用 CLI 前要执行的预处理指南。只交代用户需要操作的部分；实现接线和内部协议链接回实现区。 |

### 新写、合并和删除

- **一个规则只在所属区定义一次。** 业务含义和规范写法回到设计章节的对应规则裁决；其他文档链接到那条规则。旧实现、历史预期或兼容入口都不能反过来改写设计。已发布的工程边界由正式入口与验证证据确认，不把设计目标写成当前已支持。
- **文档和代码在同一次改动中保鲜。** 改命令、参数、目录、格式或诊断，同时查入口帮助、示例、调用方和负责说明它的文档。可运行示例应注明从哪里运行、需要什么、成功和失败怎么看，并在干净检出实际执行。设计和实现有落差时，给出可复现的实现限制，不把它写成设计规则；说明尚未验证的部分。
- **一份文档对应一项稳定任务。** 能在同一次阅读中解决的内容合在一起；只有读者、职责或变更边界不同才单独成页。删掉重复说明、矛盾草案和没有独立职责的页面；导航与机器读取所需的索引保持最薄。移动或合并时，更新所有引用并检查实际读取它们的工具。
- **样例和验收各有归属。** 种子保持稳定 ID，展示原始源码、分析副本和独立预期；预处理示例可用 Git diff 风格，但要保留完整示例和不变行。测试则保存 CLI 真正收到的完整输入，不读种子 Markdown 拼接。预期按[测试区](tests/README.md#如何写预期)独立确定。
- **只提交可长期复用的终态。** 代码、设计、接口、用法、可复验用例和维护规范进 Git；逐份保留理由、审计过程、覆盖快照、阶段清单、日志和临时输出留在仓库外。治理结论在交付时说明，不为本次治理再建一份永久审计文档。

验证命令见[实现区](implementation/docs/validation.md)。

# CLI 诊断与分析中止

## 边界：什么时候才没有 PERS

公开的 `source`、`module`、`scenario` 都分析一次调用。退出 0 代表 CLI 得到了完整 PERS；`R: void`、只有 `throws`、正常臂与异常臂并存，都可以是完整结果。业务异常由源语言及真实端口合同决定，按 [PERS-02/03/07](../../design/chapters/07-PERS登场.md#规则区) 保留其守卫、值、次序和已发生的动作；不能用 CLI 错误代替这些观察。

一次分析要覆盖所有可达路径（[SE-02](../../design/chapters/01-符号执行.md#se-02-执行覆盖与缺口)、[MV-01](../../design/chapters/02-多重宇宙.md#mv-01-分裂与覆盖)）。若其中一条走到没有可执行源码、内置定义或真实外部合同的调用，则中止本次分析，不用符号替身，不继续交付剩余路径，不把该缺口包装成用户程序的异常。诊断为 `NORM-OUT-OF-SOURCE`、`ABORT`，说明包含设计中的 `Panic: not-support`；这不是 Rust 引擎崩溃。未执行的无源码调用不得单凭这个原因使分析失败，但源码本身仍须通过导入、类型及明确的静态准入。[AI-01/04/05/11](../../design/chapters/04-AI救赎.md#交付前的准入) · [省略的两个前提](../../design/chapters/06-业务至上.md#bf-01-省略的两个前提)

| 阶段 | 何时不交 PERS | 如何跟进 |
| --- | --- | --- |
| 命令分派及启动 | 参数、入口模式或选项不对；Cargo、Node/npm 或临时目录失败 | 按用法或环境修复；不改业务输入。 |
| 清单、加载、静态准入 | 非零包依赖，目录/文件不可读，入口不唯一，导入/类型不闭合，语法、标记或类型不合合同 | 用原始路径、声明、实际接收者和失败合同修复。不要猜方法体；不把“装 npm 包”当成闭合。 |
| 语言或场景适配 | 合同未准备好，或合法结构当前无法下沉；内部载体验证失败 | 查下层证据，区分准备缺口、实现缺口和生成载体故障；合法源程序保留最小复现，不修改临时 Java。 |
| 符号执行 | 真实可达且无定义的调用，或无法保持某个操作及其实际效果 | 严格拒绝且不交部分 S/E/R；声明外部端口需要合同依据。 |
| 分析与定形 | 执行、展开、数值、候选/证明等预算未完成 | `NORM-ANALYSIS-INCOMPLETE`，不称输入无效、不产出半成品。记录入口和预算后复现。[CF-03](../../design/chapters/08-统一定形.md#cf-03-化简与候选优先级) |
| 结果构造 | 当前 PERS 无法保持业务类型、身份、表达式或循环内容 | 保留原业务关系，交规范/实现负责人；不能为了序列化而拆环或丢字段。[CF-06](../../design/chapters/08-统一定形.md#cf-06-完整-pers-验收) |
| 引擎、传输、宿主中断 | 内核不变量、未预期错误、进程起停、接收方断管或系统终止 | 不能把故障当预处理问题或业务异常；诊断、日志和部分传输均不是 PERS。 |

`help`、`errors`、`test business-examples` 是其他命令，成功的 stdout 不是 PERS。

## 接线和协议

1. **一个错误目录。** [catalog.tsv](../tools/diagnostics/catalog.tsv) 定义公开错误码、错误类别、阶段、解读、下一步和设计依据。[错误码表](cli-error-codes.md)由 `normalizer errors` 的目录渲染器生成。分类是工程接口；不会改变某项源码操作何时成立。
2. **一个公开输出边界。** `implementation/tools/normalizer` 先检查命令再初始化。分析 stdout 与诊断分别暂存，只有子步骤与清理成功且有结果才传出 PERS。Rust 诊断渲染器写公开 stderr；无法启动 Rust 时，Bash 只用同目录呈现启动和用法错误，不要求 Java 使用者额外安装 Node。成功时的诊断日志仍可走 stderr。被外部杀死、断管或写入失败不能保证交付完整字节；调用方必须检查退出状态，成功后再解析 stdout。
3. **前端只交付结果或失败证据。** TS/场景适配与内核子进程不各自渲染公开错误。子进程直接向 CLI 暂存通道写入，避免 Node 的 `spawnSync` 默认输出缓冲把大 PERS 误报为 `ENOBUFS`。场景不会套第二个公开错误码来遮盖内核故障。
4. **程序内部区分预期中止与故障。** 调用没有定义时传递类型化 `AnalysisAbort` 到 Rust CLI 边界，现阶段只是跨现有求值堆栈的非局部退出实现；这个已知类型不会触发 panic hook 或工程故障诊断。意外 panic 另报 `NORM-ENGINE-FAILURE`。业务 `throws` 不走这里。旧有阶段字符串只在渲染边界兼容解析，不能反过来决定业务执行。
5. **机器调用不解析英文。** 将 `--diagnostic-format=json` 放在分析命令前，失败 stderr 输出一个 `normalizer.diagnostic/1` JSON 对象：`code`、`kind`、`stage`、`summary`、`action`、`design`、`result: "not-produced"`，可选 `location`、`target`、`cause_code`、`tool_code`，以及 `details`。默认文本首行使用 `[CODE] kind=... stage=...`。人类正文、详细证据和底层诊断并不是二次业务分类；机器只以公开标识和进程状态为准。退出 2 表示调用用法错误，1 表示未得到完整分析结果。宿主直接终止时可能没有可读诊断或返回信号状态。

## 前置校验与下游信任

CLI 先查零包清单和闭合引用，再让语言工具及 Normalizer 的准入规则检查源码。每条静态约束归给最早拥有完整证据的一层；解析、装配、扩展指令和求值不能靠对方猜测补齐。正常交给下游的是同一份已检查 AST、实际绑定或已装载的内部载体，不是一个需要从头再猜的源文件。

| 层次 | 负责什么 | 诊断归属 |
| --- | --- | --- |
| TS 语言工具 | 使用仓库锁定的 TypeScript 编译器 API 解析、静态检查。选项固定为 strict、noEmit 和 ECMAScript 声明；不运行原工程的 ESLint、tsconfig、npm 脚本或浏览器类型库。 | 语法为 `NORM-TS-SYNTAX`；静态检查为 `NORM-TS-TYPECHECK`。位置、原始工具编号（如 `TS2322`）和详细证据可用于修复；由 Normalizer 的主码解释，不能照抄编译器不合设计的建议。 |
| Normalizer 的 TS 静态规则（lint） | 禁止关闭类型检查、绕过声明闭包、使用 `any`；不把编译器认识的所有内置方法都赋予业务语义。 | `NORM-TS-CHECK-DIRECTIVE` 或 `NORM-TS-ANY`；后者在准入处报告 `Panic: not-support`，符合 AI-04，但不是执行期无源码 `ABORT`。原生 `noImplicitAny` 的诊断仍带 TS 编号，显式和解析出的 `any` 无需伪造 TS 编号。 |
| Java 静态准入 | 仓库自身的 Java parser、绑定器及扩展感知的类型/能力校验建立源码 AST 和入口证据；这里没有另跑外部 `javac` 或第三方 linter。 | `SOURCE-PARSE-FAILED`、`SOURCE-LINK-FAILED` 和更具体的准入码。合法输入被当前解析器误拒应报缺口，不改写业务以迎合当前子集。 |
| 适配／执行／交付 | 适配器不能重新假定源码事实，内核消费已认证绑定。内部载体仍须校验自身的结构、来源和类型合同，这是另一层输入，不是把原 TS 再 lint 一遍。 | 静态事实已认证却消失是内部不变量故障，直接失败并报告 `NORM-ENGINE-FAILURE` 或 `NORM-INVARIANT`；不得补默认值或返回部分结果。未证明的合同、执行可达性、业务异常和资源预算仍分别按自己的规则处理。 |

TS 扩展指令的确定赋值是个例子：编译器不理解 `@normalizer-ir`，只有扩展感知校验已经证明**同一绑定**在实际作用域内赋值，才可消解那一处 TS2454。其他未确定赋值、编译器错误和语法守卫原样阻止执行。不能用 `@ts-ignore` 或笼统过滤整类报错取代证明。[AI-11](../../design/chapters/04-AI救赎.md#ai-11-分析副本先通过静态校验) · [RA-02](../../design/chapters/05-关系代数.md#ra-02-扩展句和宿主执行)

现行接线：原生 Java 执行与 PERS 构造只读 `SourceEntry` 保存的入口、工程根和真实绑定，不再从第二段定位符猜身份或使用默认入口。TS 的接收者路径只消费已检查的项目 AST；独立模块转到事件适配时复用已解析 AST。执行和 PERS 构造也不在载体形参绑定丢失时猜非空，不在已观察状态的来源丢失时省略身份，不把未完成的控制流当成普通 null。已证实的全异常路径不获得返回值，仍交完整的 `throws`。在扩大信任范围前，须先证明上一层已覆盖该约束；不要把所有历史校验或源码本来定义的空值行为一律删成 Panic。

## 新防御怎么加

- 回设计区确认触发前提、实际可达域和与业务异常的区别。现有代码能指导定位，不能替代设计裁决；若缺表示或语义没有定论，报告缺口，不先造规则。对于宿主类型，按 AI-01 在编译期拒绝，例如未导入也不允许默认载入 DOM 的 `KeyboardEvent`；这和可达时才中止的无源码调用不是同一种错误。
- 先找目录中的既有码。只有失败需要不同处理、且已有依据，才在目录加一行。把守卫放在掌握证据的层，只交代码和证据，不新建 stderr 格式器、分配网络退出协议或发布部分结果。旧字符串的兼容仅在诊断边界；新增内核中止应沿类型化路径，Node 适配错误使用 `DiagnosticFailure` 传递私有证据。
- 提交一个能区分该分支的独立验收输入：可达／不可达，或禁止输入／合法业务失败的对照。检查失败退出、空 stdout、单一诊断、准确位置与理由；成功对照必须比较完整 PERS。运输和启动故障用工程接口测试，不添业务种子凑覆盖。
- 更新生成表并核对链接：`implementation/tools/normalizer errors > implementation/docs/cli-error-codes.md`。可用 `node --test tests/e2e/cli_diagnostics.test.mjs` 检查目录同步、错误协议和大输出。公开字段语义或标识不向后兼容时升级诊断 schema，而不是让调用方匹配新的英文。使用区只描述如何选择恢复动作，并引用此目录。

## 尚未声称实现的能力

诊断统一并不扩展 PERS 能表达的业务语义。跨模块帮助函数依然以纯标量适配为主；一般化的无源码调用到达判定、实参一次求值、异步完成与脱链回调、精确小数及状态身份等缺口，须按相应设计规则单独验证。适配阶段报告的是实现边界，不把尚未求值的分支误报为已执行的 `ABORT`。

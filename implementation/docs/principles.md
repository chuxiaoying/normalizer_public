# Normalizer 实现原则

本文按模块展开[设计区](../../design/README.md)中的业务和架构要求，供开发者落实到解析、执行和交付合同。

## 1. 场景入口层与三模块分工

使用者面对的是多语言场景入口层，而不是语言工具的手工流水线。场景入口选择前端 VO 生产、前端 VO 消费、Java Bean、纯净 Java 等归一化场景，规定 AI 预处理合同、入口、边界和最终 PERS 验收方式；场景差异在进入统一 IR 前消失。

公共主链是：

```text
原始工程 → 场景 AI 预处理 → 多语言处理（内部）→ 统一 IR → 归一化内核 → 最终 PERS
```

| 模块 | 负责 | 不负责 |
|---|---|---|
| AI 预处理 Skill | 读懂完整原工程，闭合可达业务逻辑，整理类型、状态、对象身份、异常、端口和来源证据 | 不预先计算业务答案，不把结果改成新输入，不把未知实现填成 `null`、`0` 或固定返回 |
| 多语言解析器 | 从完整工程建立索引，按入口解析可达闭包，生成统一 IR，保留来源和未解析边 | 不替 AI 理解业务，不替内核补语义，不把语言差异泄漏给内核 |
| 归一化内核 | 对闭合统一 IR 做模拟、数学化简、状态归约和 `IR → PERS` 输出 | 不读 Java/TS/模板源码，不解析 Maven/JAR，不猜库实现或默认值 |

场景入口层负责把前端事件、组件监听、Java Bean 方法等不同入口适配为统一 IR 入口。前端 VO 生产和消费是两个场景：生产入口表达事件对 VO 的写入，消费入口表达组件或模板对 VO 快照的读取和渲染出口。内核不区分这些入口的原始语言形态。

Maven、JAR、`node_modules`、框架装配和语言运行时材料属于预处理与来源核验边界。真正的远程调用、宿主交互和业务可见副作用仍须作为显式边界交给内核表达。

## 2. 最终结果只有形式化 PERS

最终 PERS 使用 `P/E/R/S/T/throws` 表达：

- `P` 是入口参数；
- `E` 是按观察时点取得的环境、入口字段或边界响应；
- `R` 是分析入口的正常结果；
- `S` 是按因果顺序记录的字段写入、真实外部调用和其他可观察副作用；
- `T` 是定义完整的纯值、递推或关系；
- `throws` 是异常完成及其载荷。

形式化结果不包含自然语言需求描述、执行式 `if`、赋值、`load/store` 或 `return`。`CASE WHEN ... THEN ... ELSE ... END`、纯 `T` 定义和结构化 `S` 记录是结果表达形式，不是把程序语句原样搬进 PERS。解析器内部材料、内核调试输出、日志、来源说明和 AI 生成的自然语言解释都属于辅助观察层，不能冒充统一 IR 或最终 PERS，也不能反过来修改 PERS 预期。

## 3. 前端事件、VO 与组件消费

前端 `onMount`、`onClick`、`onInput`、store action 等事件或生命周期函数可以作为分析入口。严格双向绑定时，VO 是生产与消费之间的唯一业务连接：

| 前端事实 | PERS 归类 |
|---|---|
| 事件参数、初始化参数和入口上下文 | `P` |
| RPC/HTTP 响应或入口状态字段的读取 | `E` |
| RPC/HTTP 调用及其参数、顺序和失败 | `S` 中的边界记录 |
| 事件对 VO 字段的写入 | `S` 中的 VO 写入 |
| 组件属性、显示条件、文本和样式对 VO 的读取 | 消费侧 `E` |
| 组件属性最终形成的视觉结果 | 消费侧 `R` |

生产归一化和消费归一化分开完成，再通过同一个 `VO.field` 或 `VO.field.subfield` 建立链接。生产侧不能把组件样式提前写成答案，消费侧不能把模板条件挪回生产侧。一个 VO 字段可以被多个组件消费，每个组件的属性和归属必须分别保留。

例如配置 RPC 写入 `VO.darkMode`，生产侧记录响应、判断和 VO 写入；消费侧以 `VO.darkMode` 为 `E`，分别产生 `BackgroundPanel.style.backgroundColor` 和 `TextLabel.style.color` 的 `R`。这两侧的连接通过 VO 字段建立，不因最终颜色相同而合并组件观察。

## 4. 业务逻辑优先与原生操作封闭

内核复杂度应优先投入订单、金额、状态、条件、对象身份、别名、异常、真实调用及其顺序等业务逻辑。JDK、Maven、框架内部步骤、编解码和普通库实现细节，先沿 AI 预处理或已有原生语义操作闭合。

原生操作必须保持自己的封闭合同：输入类型、适用域、结果、异常和可观察副作用必须在操作边界内定义完整。不要为了“看见更多内部步骤”把一个已封闭且业务不可观察的原生操作拆成一串没有业务意义的伪调用，也不要把真正影响业务的本地校验、缓存、重试、状态写入或转换隐藏成一个黑盒端口。业务可见的部分继续展开，纯实现细节保持在原生操作或预处理边界内。

### 无源码依赖的封闭原则

本次 AI 交付中没有提供源码、经过审查的等价规范源码或完整扩展语义的 JDK、第三方 JAR、运行时和框架实现，一律视为**无源码依赖**。Normalizer 不读取、反编译、猜测或模拟这类依赖的内部实现；“本机恰好存在源码”“类名或方法名看起来熟悉”以及“可以通过原生运行得到样例结果”都不能把它们变成可分析的业务源码。

没有实现的业务方法或普通对象调用不构成 external。AI 可以交付有依据的规范源码或已定义的闭合语义，此时内核看到的是完整计算，不是无源码调用。真正离开观察范围的调用必须有合法 external 声明并进入 S。其余缺口应在预处理报告；若仍到达内核，Panic 并报告不支持，不产生 PERS。详见[规范源码合同](../contracts/normalized-source-contract.md)与[种子交付索引](../skills/normalizer-preprocess/references/seed-coverage.md)。

## 5. 统一正则规范与 expected 原则

每项支持的语义先用具体常量检查执行结果，再用符号输入检查归约和 PERS。常量写在源码里就原样交付；已知值不授权 AI 替内核出结果。见[规范源码合同](../contracts/normalized-source-contract.md)。

规范规则先于测试 expected。交换律、结合律、幂等、CASE 取向、整数域、引用身份、E/T 编号和字段顺序都由统一规范合同决定。等价候选只有在满足以下条件后才能比较：

```text
semantic_equal(input, candidate)
preserves_observation_and_lazy_domains(input, candidate)
complexity_equivalent(input, candidate)
```

规范改写不能增加真实调用、观察、分配、分支或递归边界。允许交换的加法或乘法统一收集叶子、排序并固定左折叠；完整 CASE 才能在证明互补、惰性和观察域不变后同时交换条件与两臂；部分 CASE 不补 `ELSE`。

每个入口只接受一份从源码、观察范围和规范合同独立推导的完整 expected。禁止从 actual 反填 expected，禁止为迎合不同测试的偶然写法增加 pattern 补丁、切换格式或在断言前重新化简 actual。发现“修好 A 又破坏 B”时，回到共同规范、语义域或预处理闭合条件，不能继续堆局部补丁。

## 6. 对象身份、环和边界出口

内部 heap 的身份、别名、分配和循环必须完整模拟，但它们不自动成为最终输出。内部函数的 `return` 继续用于模拟；只有分析入口的 `R`、RPC 参数和可观察 `S` 按出口合同投影内容。

- 共享引用、字段别名和自环会影响业务结果，不能批量删除身份测试；
- 内部有环但最终投影是普通有限值时，继续归一化；
- 最终 `R`、RPC 参数或可观察 `S` 的完整投影含环时，明确 abort，不截断对象、不伪造新引用编号；
- 无序 Set 的内容使用 `map<member,true>` 投影，保留去重和 null 边界，不承诺偶然迭代顺序；
- 新对象只有在其身份或有限字段内容进入已声明观察范围时才影响最终 PERS。

## 7. 回归测试原则

- Java 是测试 Java 解析、绑定和内核的主线；
- JavaScript、TypeScript、前端框架和其他语言补充 parse、绑定和语言特有语义，并以少量案例验证共享内核接线，不重复铺完整内核矩阵；
- 完整欠费单、整页 handler 链路、大型业务 oracle 和真实 Maven/JAR 依赖不进入常规 feature 门禁；从中抽取最小、自包含、可独立推导的 feature fixture；
- 每个测试只证明一条必要的分支、状态、异常、身份、顺序或边界差异；禁止无理由的字符全域穷举、笛卡尔积和重复压力规模；
- 最终 PERS 断言、内核调试输出、原程序对照、来源方程和材料账本各自承担职责，不能互相冒充；
- 失败场景不能通过删除、缩小输入、`ignore`、`abort` 或放宽断言来伪造通过。

## 8. 证据驱动的修复方式

先复现，再归因。每次排查至少记录基线提交、fixture、入口、运行命令、阶段、日志路径、输入摘要、错误和状态转移。优先使用已有 debug/profile/trace 能力，通过最小定向复现补足证据；证据不足时补观测，不靠反复猜测和试错。

修复必须回到实际责任层，并用同一证据链复跑，检查 R/E/S/T/throws、异常、身份、顺序和相关 case 是否同时保持。只改代码、没有复现和回归证据，不能称为已解决。

## 9. AI 后处理的边界

AI 可以在所有归一化结果完成后，将 PERS 和独立证据提炼为自然语言需求描述，供人理解和文档展示。这个后处理结果不是内核输入、不是 PERS、不是 expected，也不能反向驱动规范形式选择。

# normalizer 文档范围

normalizer 仓库里的文档只描述可复用的产品合同、工具接口、Skill 规则、稳定的验收标准和可复现使用说明。新 agent 应该只依赖这些内容完成任务。

对使用者而言，文档的第一入口是场景 README。场景 README 必须把原始工程、AI 预处理合同、入口、边界、场景 CLI、统一 IR 交付和最终 PERS 验收写完整；`implementation/tools/frontend` 的内部解析材料、单次过程脚本和调试输出不能替代场景入口文档。

## 应进入 Git 的内容

- 三模块架构和模块交接合同；
- AI 预处理 Skill 及其语言/框架参考；
- 工具的输入、输出、schema、限制和可重复命令；
- 项目入口、边界元素、验收规则和稳定结果；
- 能够独立复现、与当前仓库版本绑定的小而完整的 feature fixture、独立完整 PERS 预期及可复用测试说明。

提交前要去掉个人绝对路径、临时目录、对话过程和只对一次试验成立的数字。结果必须能由文档中的入口和当前代码重新得到，不能依赖某个 agent 的聊天上下文。

## 只留在本机任务记录的内容

- 空白 agent 的提示、过程对话和阶段性判断；
- `/tmp` 下的源码适配器、原始工具输出、调试文件和中间 JSON/YAML；
- 尚未稳定成 schema 的探索性输入；
- 为定位 bug 临时复制的外部项目文件；
- 只用于本轮验证、没有复用价值的命令日志。

这些材料可以支持验收，但不构成产品流程。正式文档只能描述它们验证出的规则和结论，例如“真正的远程或宿主交互保留为显式端口；内部 dispatch 和 helper 保留完整实现”，不能要求新 agent 依赖某个 `/tmp` 文件才能完成工作。

## 实战材料与 feature 回归的边界

真实业务工程、完整页面／handler 的临时改写、依赖快照、业务 oracle 和单次实战说明保存在仓库外，不作为 normalizer 每次必须通过的整页门禁。仓库保留从实战提炼的通用工程／Skill 改进，以及有独立完整 PERS 验收的小 feature；材料归档不表示其行为或最终输出已经通过。

feature 的“小”指观察范围聚焦，不能以删掉可达计算换取代码短小。入口内的 helper、响应转换、状态关系和失败路径仍须完整；只有真实远程服务和宿主交互可声明为端口，不能把内部 helper 换成端口，也不能新增预计算业务答案入参。完整业务 VO 图、整页依赖和业务 oracle 不应改个名字搬成小 fixture。

整理旧材料时先确认通用观察的去向。已有独立 feature 的，写清对应入口及完整 PERS 测试；尚无替代的，保留观察证据并明确它不再属于哪一项验收范围，不能以移走失败测试宣称能力修复或覆盖未变。稳定文档描述通用三模块用法，不依赖某次业务实战的工具目录、源码路径或过程清单。

## 设计文档与任务记录

正式文档写模块职责、语义合同、输入输出、规范化原则及可复现命令，不写按日期推进的计划、阶段完成数量、单次失败清单或个人环境记录。阶段状态保存在任务记录，历史可从 Git 追溯；保留 fixture 来源、独立预期推导和必要行为证据，它们属于测试依据，不是可随意清除的任务日志。

终态设计明确规则和责任，不将尚未实现的能力写成当前事实。实现缺口由实际 gate、诊断和测试清单表达；正文不因某次绿灯改变合同，也不以手工更新黄金掩盖失败。

# 种子分母与覆盖模型

`seed-plan.yaml` 是设计种子的分母计划。它枚举当前认为需要独立人机对齐的语义场景。`seeded` 表示已经有设计种子，`planned` 表示只占分母位置。已实现种子的 `test_status` 只表示 CLI 覆盖状态，取 `pending` 或 `covered`。种子与 Normalizer 重构的协作阶段由独立的 `review_status` 表示，取 `proposed`、`challenged`、`revised`、`accepted` 或 `cli-passed`，不再把审核阶段混入测试覆盖状态。

当前分母包含 101 个种子位置，其中 75 个已有设计种子，26 个等待补齐。第四轮审核将原本混合“等式唯一规范”和“等式／不等式联立求解”的一个位置拆成两个独立语义合同，因此分母从 100 调整为 101。第五轮补齐了 switch 分支、外部结果复用和实例方法入口三个既有位置。第六轮补齐了金额精度合同和 JDK 越界拒绝两个既有位置。第七轮补齐了未知布尔条件路径一个既有位置。第八轮审查把超时 fallback 收为已有外部标量种子的变体，没有新增重复分母位置。第九轮补齐了除零合同未闭合时的明确拒绝边界。第十轮补齐了原生 throw/catch 路径未闭合时的控制流拒绝边界。第十一轮补齐了等式与不等式联合约束规范化。后续轮次补齐了显式状态标记、状态嵌套别名和外部对象整体返回，另为业务回卷种子补齐了 CLI 派生测试。本轮补齐了 CASE 内局部重复的 LET 规范种子、嵌套记录字段投影种子、可空字段类型合同种子、结构相等／引用身份对照种子、finally 有序状态写入种子、多次写入读取时点种子、跨入口状态根种子、变量有限边界循环种子、break／continue 循环汇合种子、递归终止拒绝种子、关系删除写入种子、关系排序 LIMIT 种子、SQL NULL 语义种子、关系 JOIN 种子、分组聚合种子、小数舍入种子、空集合首项种子、集合 map 种子、带初值 reduce 种子、重复元素去重种子和嵌套集合种子。这个数量来自语义场景矩阵的逐项枚举，不代表把所有 Java、JavaScript 或 TypeScript 语法逐条复制一遍。一个种子应覆盖一个可独立判断的业务语义，语法变化在已有语义合同下通过派生测试覆盖。

## 为什么这组分母能够验收各种代码场景

设计种子按五个互相独立的观察维度展开。

| 观察维度 | 覆盖的种子区域 | 代表问题 |
|---|---|---|
| 执行形状 | 控制流、循环与终止、语言入口 | 路径如何分裂，循环何时可知，入口如何确定 |
| 数据形状 | 集合、对象与类型、关系数据 | 标量、对象、数组、Tuple、表和列如何进入 PERS |
| 可变性 | 状态与别名、基础合同 | 哪些写入进入 S，别名怎样观察，空值合同怎样表达 |
| 计算规则 | 表达式化简、数值域 | 如何化简，如何求解约束，业务 number 如何脱离机器位宽 |
| 边界与预处理 | 外部边界、语言入口、联合主题 | 外部库、SQL、回调、循环和非原生结构如何交给工程 |

这五个维度覆盖了符号化执行必须处理的主要变化来源。任意一个代码场景都可以先按执行形状、数据形状、可变性、计算规则和边界进行定位，再选择一个主种子。多个维度同时成为测试重点时，进入联合主题，观察组合后新增的业务规则。

AI 预处理也属于种子覆盖范围。以下预处理动作在分母中有明确位置：

- 在声明处增加 `external`、`state` 等标记
- 只替换一行中的库调用或 invocation
- 删除循环片段并以保持原语言合法的标记注释表达局部 IR
- 将 SQL、集合库调用和外部库调用转换为标准业务语义
- 对前端代码进行 entry 级重构
- 对无法证明终止的循环或无法保留语义的源码明确拒绝

这些条目分别落在外部边界、循环与终止、关系数据、语言入口和联合主题中。测试重点在 AI 交付物时，种子正文必须同时展示原始源码、预处理结果和最终 PERS。测试重点在内核语义时，预处理只提供进入原生解析器的最小改动。

## 分母和测试分母的关系

设计分母与 CLI 测试数量保持两个层级。

```text
一个设计种子
  → 一个或多个真实入口
  → 每个入口一个原例
  → 每个入口多个业务变体
```

`seed-plan.yaml` 的 101 个条目是需要建立人机对齐的语义分母。`seeds.yaml` 只登记已经拥有完整设计正文的条目。`tests/e2e/catalog.yaml` 只登记已经可以由 CLI 运行的入口和变体。一个 planned 种子必须先补齐设计正文，再进入测试清单。

这种分层可以分别回答三个问题：

1. 设计空间还有哪些语义位置没有被案例覆盖。
2. 哪些语义已经有完整的原始代码、预处理结果和 PERS。
3. 哪些已完成种子已经通过真实 CLI 入口验收。

收集器会强校验已实现种子都位于分母计划内，计划总数、已实现数和待补数与清单一致。计划条目不会被当作测试通过，也不会生成虚假的 expected。

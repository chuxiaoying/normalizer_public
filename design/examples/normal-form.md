# PERS 统一规范形式

这份文档说明设计种子和测试 expected 如何选择唯一的 PERS 表达，以[内核归约规则与规范形式合同](../../implementation/contracts/kernel/normal-form-contract.md)为准。

## 目标

同一业务语义只能有一个可接受的 expected。`a + b` 与 `b + a` 只有在已证明属于同一纯、可交换、可结合的数值运算族时才汇合。测试不能把“语义等价”当成“两个 expected 都合法”，也不能为了适配某次 CLI 输出把 actual 直接抄回 expected。

统一规范形式必须满足以下条件：

```text
semantic_equal(input, candidate)
preserves_observation_and_lazy_domains(input, candidate)
complexity_equivalent(input, candidate)
```

表达式必须保持相同的取得域、惰性边界、异常域、调用次数、观察次数、分配次数和递归边界。无法证明这些前提时保留原结构并报告规范缺口。

## 可以排序的同类项

只有已经证明纯、总、同类型且可交换的同类项才收集、排序并按固定方向重建左折叠树。

- Boolean `AND`、`OR`
- 精确业务 `number` 的 `Add`、`Mul`
- 其他运算只有在自己的合同明确宣布可交换、可结合时才加入

排序依据是统一 IR 的结构比较键，不是最终渲染字符串。比较键使用公开业务路径、类型、运算族和稳定结构。内部 heap id、临时绑定 id、函数注册顺序、HashMap 遍历顺序和输出中的偶然编号不能成为业务排序依据。

```text
normalize(add(b, a)) = normalize(add(a, b))
normalize(add(c, add(b, a))) = normalize(add(add(a, b), c))
normalize(and(b, a)) = normalize(and(a, b))
normalize(normalize(x)) = normalize(x)
```

`String` 拼接、函数参数、数组和 List 元素、Tuple 或有序记录字段、关系输入顺序、真实调用顺序和 S 事件顺序都不能套用这套排序。

## 比较方向

`Lt`、`Le`、`Gt`、`Ge` 在参与排序或 CASE 取向前先统一操作数方向。换边必须同步交换比较符号，`a > b` 与 `b < a` 才能进入同一个比较结构。这个改写只重述已经存在的纯比较，不改变源程序的求值顺序、取得域、调用、异常或惰性。

比较方向统一后，才对同类项建立结构键。`Eq` 和 `Ne` 继续遵守各自合同，不能用字符串顺序替代语义比较。

## CASE-WHEN

CASE 分支保留源码的首命中顺序，不能像 AND、OR 或 Add 项一样排序。每个分支显示的是前面分支失败后的剩余域中的当前条件，因此后续分支不重复拼接已经由首命中语义承担的 `NOT` 条件。

```text
CASE
  WHEN p THEN y
  WHEN true THEN n
END
```

只有在条件互补、两臂可交换、没有改变取得域、异常、调用、观察或惰性时，才允许同时取反条件并交换两臂。不能只取反条件而保留原结果顺序，也不能给部分 CASE 擅自补 ELSE。

CASE 的分支重复合并必须保持首命中语义、正常返回覆盖、throws 可见性和 S 顺序。无法证明合并安全时保留分支。

## 数值域

普通业务 `number` 使用精确数学整数，不受 Java `int`、`long` 或 Rust 存储位宽限制。`MAX + 1` 仍是数学上的下一个整数。源码显式要求回卷、窄化、饱和或其他机器行为时，必须作为独立 word 或业务操作保留，不能混进普通 number 的化简。

浮点 NaN、无穷、舍入、有符号零和字符串顺序不能套用普通整数或实数恒等式。除法、除零和舍入也必须有自己的业务合同。

普通精确整数的加法、乘法只做有证据的结合、交换、常量合并和恒等值化简，不默认展开分配律或进行因式分解。更大范围的数学变换必须先发布唯一方向、前提和停止条件。

## R、throws、E、S、T 的边界

- `R` 只表达正常返回值。只抛异常的路径进入 `throws`，不能在 R 中伪造 `null`、`0` 或默认值。
- `E` 表达已取得的环境、状态、表和外部结果来源。`P` 表达入口参数。局部别名不能被提升为新的业务来源。
- `S` 是有序可观察事件，真实调用、状态写入、SQL 写入和异常完成顺序不能按结构键排序。
- `T` 只在既定提取规则成立时出现。局部绑定不能改变调用次数、观察域或异常域。
- E、S、T 和 throws 中的引用必须随内部绑定的稳定重命名一起更新。不能在断言前删除编号或用任意名称映射掩盖不稳定。

## expected 的验收方式

每个 PERS expected 必须由源码、AI 预处理结果和统一规范形式独立推导。测试至少包含：

1. 可交换项的不同排列和不同括号。
2. CASE 条件、两臂方向和首命中顺序的等价写法。
3. `normalize(normalize(x))` 的幂等性。
4. 改变阈值、参数、调用顺序、异常或状态读取时点的反例。
5. 破坏规范前提后的拒绝或保留原结构行为。

断言严格比较完整 PERS，包括 `schema`、`entry`、`P`、`E`、`S`、`T`、`R` 和 `throws`。不能先把 actual 和 expected 一起送进同一个生产化简器，再以“等价”放宽断言。

当实际输出与 expected 不一致时，必须先分类：源码推导错误、观察合同错误、规范形式错误、内核归约错误或规范尚未定义。没有完成分类前，不得直接改 expected。

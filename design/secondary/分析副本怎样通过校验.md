# 分析副本怎样通过校验

生产源码照常由原语言的工具链编译。AI 交给 Normalizer 的是**分析副本**：外层还是 Java 或严格的 TypeScript，可在声明和语句位置补入受约束的扩展语义。分析副本需要通过 Normalizer 的校验，不要求忽略注解和指令以后还能拿去部署。

原始模板、原框架工程和改写对照只供 AI 预处理与人工复核，不是分析副本的组成部分，也不能成为 CLI 的运行前置条件。前端观察的源码身份由分析模块中的入口定位和相应声明标记交付。

交付必须满足以下条件。扩展的绑定要纳入静态校验；所有准入检查必须在开始模拟执行前完成。

1. **定位入口并解析。** Java 从静态方法或已装配的静态接收对象定位调用，TypeScript 从模块导出的函数或已导出对象上的方法定位。统一用「工程相对路径#入口调用」，不填具体实参；重载有歧义才在定位中加原语言参数类型。解析宿主语法时保留扩展标记及其源码位置，普通说明注释照常忽略；受保留语法约束的未知标记不能静默略过。
2. **静态检查同时覆盖指令和原生语句。** 在原语句位置绑定扩展指令，和原生语句一起核对类型、作用域、路径上的确定赋值及异常合同。从 Java 入口可达的类型引用只允许工程内定义、Normalizer 内置类型和规范承认的原生值类型；TypeScript 的 `any` 不得进入分析副本，`unknown` 按[宽类型值规则](../chapters/01-符号执行.md#se-03-宽类型值按源码语义执行)处理；见 [AI救赎的正反例](../chapters/04-AI救赎.md#只支持强类型)。
3. **确认边界后交给内核。** 有限计算用可证明的边界；无法逐步展开的循环要有等价且定义清楚的整体表达。外部调用要有可解析的接收者、接口与明确的成功类型。已声明的异常类型也必须可解析；没有失败声明时不建立外部异常路径，见[外部异常须显式声明](../chapters/04-AI救赎.md#ai-09-外部异常须显式声明)。校验负责判断交付物能不能分析，不提前替内核决定分支结果。

例如以下是完整的 **分析版** `Count.java`。表 `bill` 的契约另由分析工程提供。

```java
class Count {
    static int run() {
        int rows;
        /* @normalizer-ir rows = count from bill as b */
        return rows;
    }
}
```

指令在 `return` 之前给 `rows` 赋值，所以能通过扩展感知的初始化检查。若指令只在一个条件分支里赋值，就不能在另一条未赋值路径直接返回 `rows`。补个 `= 0` 不是修复，那会凭空给这条路径一个结果。

**分析拒绝不是业务异常。** 未绑定类型、未知指令或无法解析的调用声明，应返回带源码位置的分析诊断，不生成 PERS。比如返回 `Promise<Receipt>` 的外部方法，在 `Receipt` 已解析且没有 `rejects` 时可正常分析；若写了 `@N rejects MissingError` 但找不到该类型，就拒绝这份交付。不支持的类型或尚未定义的调用报 `Panic: not-support`，预算不足则报告分析未完成。一个合法入口在执行中可能发生的数组越界、端口失败等，才按业务可达路径记入 PERS；此前发生的写入不被抹掉。

## TypeScript 宽类型值的检查

`type Payload = unknown`、直接标注的 `unknown`、字段中的 `unknown` 和推导出的 `unknown` 都按同一规则处理。比如 `read(value: Payload)` 可用 `typeof value === "string"` 建立文本路径，也可直接把值交给接收 `unknown` 的函数。不允许把没有收窄的值直接当作字符串返回；类型断言本身不做运行时检查，不能据此移除原有的失败路径。

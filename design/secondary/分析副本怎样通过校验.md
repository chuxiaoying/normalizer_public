# 分析副本怎样通过校验

生产源码照常由原语言的工具链编译。AI 交给 Normalizer 的是**分析副本**：外层还是 Java 或严格的 TypeScript，可在声明和语句位置补入受约束的扩展语义。分析副本需要通过 Normalizer 的校验，不要求忽略注解和指令以后还能拿去部署。

原始模板、原框架工程和改写对照只供 AI 预处理与人工复核，不是分析副本的组成部分，也不能成为 CLI 的运行前置条件。前端观察的源码身份由分析模块中的入口定位和相应声明标记交付。

校验按这个顺序进行：

1. **定位入口并解析。** Java 从静态方法或已装配的静态接收对象定位调用，TypeScript 从模块导出的函数或已导出对象上的方法定位。统一用「工程相对路径#入口调用」，不填具体实参；重载有歧义才在定位中加原语言参数类型。解析宿主语法时保留扩展标记及其源码位置，普通说明注释照常忽略；受保留语法约束的未知标记不能静默略过。
2. **解析指令后再做完整静态校验。** 在原语句位置绑定扩展指令，和原生语句一起核对类型、作用域、路径上的确定赋值及异常合同。从 Java 入口可达的类型引用只允许工程内定义、Normalizer 内置类型和规范承认的原生值类型；TypeScript 不接受 `any`。外部形状可以先作为 `unknown`，但使用具体字段前须有原语言的有效检查和类型收窄，不能靠断言把未知当已知。
3. **确认边界后交给内核。** 有限计算用可证明的边界；无法逐步展开的循环要有等价且定义清楚的整体表达。外部调用要有可解析的接收者、接口和完成合同。校验负责判断交付物能不能分析，不提前替内核决定分支结果。

例如以下是完整的 **分析版** `Count.java`。表 `bill` 的契约另由分析工程提供。

```java
class Count {
    static int run() {
        int rows;
        /* @normalizer-ir rows = count from bill as b */
        return rows;
    }
}
```

指令在 `return` 之前给 `rows` 赋值，所以能通过扩展感知的初始化检查。若指令只在一个条件分支里赋值，就不能在另一条未赋值路径直接返回 `rows`。补个 `= 0` 不是修复，那会凭空给这条路径一个结果。

**分析拒绝不是业务异常。** 未绑定类型、未知指令或没有闭合的调用合同，应返回带源码位置的分析诊断，不生成 PERS；不支持的类型或尚未定义的调用报 `Panic: not-support`，预算不足则报告分析未完成。一个合法入口在执行中可能发生的数组越界、端口失败等，才按业务可达路径记入 PERS；此前发生的写入不被抹掉。

## 入口的 unknown 与运行时收窄

TypeScript 的 `unknown` 可以保留为入口接收的原始值，不能为了分析把它提前声明成 `text`、给入口增加「已通过检查」的布尔参数，或做 `String(value)` 转换。它不是可作业务运算的原生类型。P 可以声明 `type: unknown`，R、E、字段和命名类型不能用这个类型表示已取得的业务值。

先有原生运行时检查，再使用同一值的收窄结果。例如 `typeof value === "string"` 对包括 null、undefined、闭包和对象包装在内的宿主原始值作类型区分，空字符串仍通过。成功路径上的 `R: value` 指向原字符串；失败路径用 `throws.when: 'typeof(value) != "string"'` 表达，并保留源程序实际抛出的类型与消息。这个 PERS 谓词是源语言类型测试，不替换成真假判断，也不执行任何转换。

其他收窄方式也须由原语言的有效检查和控制流证明。一个入口的检查不为另一个入口或未经过验证的值提供类型证据。

# 场景归一

想象一个没有外部依赖的 Java `main` 函数。谁把参数交进来，从哪一句开始，顺着哪些函数走，在什么地方结束，沿源码都能说清。一个普通静态方法也可以是这样的入口，例如 `static int addOne(int x) { return x + 1; }`。即使不知道调用者会传几，Normalizer 也能从这个入口得到 `x + 1`。

这就是**标准函数入口**。给定一次调用，能从源码定位要调的函数，以及它用的是哪个实例。从那里出发，业务代码和依赖都有着落。库里的计算，有等价标准库函数就交成那个函数。SQL 查询可以交成关系代数这样的扩展语义。真正发到外部服务的调用，则按端口合同记入 S。函数可以读状态、写状态、发请求、抛异常。只要准备好的程序满足《AI救赎》的要求，都可以从这个入口归一化。[AI救赎](04-AI救赎.md)

生产系统把「谁调用谁」藏在了不同地方。服务端的一条路由会调到某个已装配的对象，网页上的一次点击会调到页面实例的处理器，一次渲染会对模板里的属性求值。**场景归一要做的，就是找到原系统已经在做的那次调用，把它写成标准函数入口。** 分析整页时可以找到许多个这样的入口，每次归一化仍从一个函数开始。

## Java 服务端 · 容器把请求交给了谁

一个 HTTP 接口和一个 RPC 接口都可以从「请求已经绑定成业务参数，开始调用服务方法」分析。困难往往在调用之前。以 Spring 为例，路由表能告诉我们调用哪个方法，但对象由容器创建，方法里用的服务也可能由容器按配置注入。光看到方法签名，还不知道这次执行会走进哪份业务实现。

假设下单接口的构造器接受 `Pricing`，当前配置注入的是 `RetailPricing`，两者都能在业务源码里找到。下面只列装配和入口，`quote` 的方法体沿用原件。

```diff
-@RestController
 class OrderEndpoint {
     private final Pricing pricing;
     OrderEndpoint(Pricing pricing) { this.pricing = pricing; }

-    @PostMapping("/quote")
-    int quote(@RequestParam("units") int units) { return pricing.quote(units); }
+    int quote(int units) { return pricing.quote(units); }
 }
+
+class Beans {
+    static final OrderEndpoint ORDERS = new OrderEndpoint(new RetailPricing());
+}
```

现在从 `Beans.ORDERS.quote` 就能发起同一次业务调用。静态可达的是**取得接收对象的路径**，`quote` 仍是实例方法，注入的计价逻辑仍要执行。若观察范围从收到原始 HTTP 请求开始，缺参、绑定失败以及原接口怎样响应也在范围内，上面的起点只覆盖成功绑定之后。

常见的无状态服务可以长期持有同一个实例，却把每次请求的临时数据都留在这次调用里。识别状态要问的是：**上一次请求留下的值，会不会改变下一次请求的业务行为？** 例如库存只保存在这个实例的 `remaining` 字段里，下次下单还得用上次扣完的数，就要显式标记 `@N.EntryState`。入口读到的原有库存属于 E，扣减写回属于 S。仅影响速度的缓存可以没有独立的业务状态身份，缓存命中若会改变对外调用，则仍须保留这种差别。普通堆对象和缓存代码照原程序执行。[业务至上](06-业务至上.md) · [PERS 中的库存与创单](07-PERS登场.md)

## 前端生产 · 一次事件给页面留下了什么

在浏览器里，应用代码往往没有一个写在最外层的 `main`。用户点击按钮，浏览器捕获事件，框架找到对应的页面实例，最后才轮到应用写的 handler。显式监听、模板里的事件绑定、框架转交的生命周期回调，写法不同，都要沿真实触发关系找到应用接手的地方。

看一个订单页面的两个绑定。用户点击「加一件」，卡片显示新的数量。这里的 `draft` 属于当前页面实例。

```vue
<template>
  <button @click="addOne">加一件</button>
  <OrderCard id="summary" :units="draft.ready ? draft.units : 0" />
</template>

<script setup lang="ts">
import { reactive } from "vue";

const draft = reactive({ units: 0, ready: false });

function addOne(): void {
    draft.units += 1;
    draft.ready = true;
}
</script>
```

生产归一化从点击真正进入的 `addOne` 开始。模板和响应式容器脱糖后，交出的生产入口如下。模块里的 `draft` 代表刚才那个页面实例，初始化发生在创建实例时。

```typescript
import * as N from "@normalizer/stdlib";

/** @N entryState */
const draft = { units: 0, ready: false };

export function addOne(): void {
    draft.units += 1;
    draft.ready = true;
}
```

假设点击前已经有 4 件，这次就写入 5，再把 `ready` 写成 `true`。单独分析这次点击时，原有数量未知，它来自 E。两次写入按实际顺序进入 S。声明里的初值 0 不能代替点击前的数量。

这里把页面持有、会影响后续业务或展示的状态称为 **VO（visual object）**。VO 要主动标记。一个选中的订单号即使从未显示，只要下次提交还要读取，也属于页面的业务状态。反过来，handler 为了算新数量临时开一个局部变量，它同样在内存里，却只参与这次计算。

handler 还可能发 HTTP 或 RPC 请求，或调用宿主的支付接口。这些真实的外部调用都进入 S，回执由发生调用的那一步绑定。成功后写 VO、失败后提示用户，就分别保留在各自路径上。一个事件即使只发出了请求，也值得从它的真实 handler 分析。[PERS 中的外部调用与回执](07-PERS登场.md#pers-01-参数环境和回执的来源)

## 前端消费 · 这一次渲染给属性什么值

再看同一页的另一半。以输入框为例，用户编辑会更新绑定的状态，程序改了状态，框架又会把新值填回输入框。双向绑定把这两个方向写在了一起。上例用 `@click` 和 `:units` 分开写，两个方向就一眼可见。沿着状态流向界面的一边看，最终可以指到具体使用点，例如某个 `div` 的 `title`，或这里 `OrderCard#summary` 的 `units`。

消费归一化把这个属性的取值表达式写成一个**同步、无参的取值函数（supplier）**。在上面的同一份分析模块里，补上这个导出函数，就有了消费入口。

```typescript
/** @N componentProp OrderCard#summary.units */
export function cardUnits(): number {
    return draft.ready ? draft.units : 0;
}
```

调用 `cardUnits()` 相当于问「此刻给这张卡片多少件？」当次求值开始时的 VO 来自 E，交给属性的值就是 R。假设现有数量都是 4，`ready` 为真时卡片得到 4，为假时得到 0。可以直接从这两种状态分析，无须先模拟用户点过几次按钮。这样，生产和消费通过**同一页面实例的同一份 VO** 对得上，两个入口又各自说得清。[属性入口的约定](04-AI救赎.md#ai-10-组件属性投影必须同步无参) · [属性入口的完整 PERS](07-PERS登场.md)

## 规则区

### SC-01 入口保留原场景的调用起点

HTTP 或 RPC 从约定的服务边界开始，前端生产从宿主直接或经框架转交给应用的回调开始。预处理把触发和实例装配写明，保留从这个起点到完成之间的业务判断、状态和对外动作。

**示例**　按钮绑定 `onSubmit`，处理器先检查能否重复提交，再调 `orders.create`。选 `onSubmit` 为入口，两条路径分别是拦住这次提交和发起创单。若跳到同样可调用的 `orders.create`，就会把本来被拦住的点击也算成创单。

### SC-02 跨调用的业务状态要能认回同一个对象

按实际所有者和实例标记状态。读取入口已有的业务值归 E，后续读到自己刚写的值沿用那次写入，可观察写入归 S。Java 的实例字段和前端的响应式对象都按这个标准辨认。

**示例**　同一时刻打开两张订单页，各自有独立的草稿。第一张的点击写第一张的 `draft`；第二张卡片求值仍读第二张的 `draft`。把两份草稿都换成一个全局对象，会凭空造出跨页面的业务影响。

### SC-03 一次消费对应一个实例的一项实际观察

属性入口保留模板上「哪个实例、哪项属性、何时会求值」的对应关系。分析整页生产要找全实际的业务回调，分析整页消费要找全实际的展示和交互属性观察。两侧都由原页的绑定确定范围。

**示例**　若把订单卡片包在 `v-if="visible"` 里，`visible` 为真且 `draft.ready` 为假时，卡片收到 0。若 `visible` 为假，卡片没有挂载，根本没有这次 `units` 求值。两种结果在页面上有清楚的区别。

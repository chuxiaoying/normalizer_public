# 场景归一

Normalizer 最初面对的问题很小：**给我一个函数，告诉我调用它一次会发生什么。** 一个没有外部依赖的 Java `main` 最容易理解。参数从函数签名进来，第一句就在那里，沿着它调用的代码走到结束，分析范围也就确定了。

前面几章让这个办法走得更远。库里的计算可以归入标准库，藏在 SQL 里的查询可以交成关系代数这样的扩展语义，确实要发到外部去的请求则留下一个 S。入口用到的接收对象也可以在预处理时装配好，从源码里就能直接发起调用。这样得到的函数仍和 `main` 一样好找，走进去以后，每个依赖都有交代，计算也满足第四章的有界要求。我们把它称为**标准函数入口**。[AI救赎](04-AI救赎.md)

**凡是满足标准函数入口的程序，都可以归一化。** 这句话决定了怎样支持真实系统：每遇到一个新场景，先问它怎样映射为一次或几次标准函数调用。把 Spring 的装配、浏览器的事件派发、模板的属性绑定解释清楚，是场景预处理的责任。交到内核手里的，始终是从一个已知入口出发的原生程序。

## Java 服务端 · 让运行时装配的服务静态可达

互联网服务端天然就有业务入口。对方发来一个 HTTP 或 RPC 请求，应用总要有一个方法接手。真正拦在标准入口前面的，往往是这个方法属于谁、它又依赖谁：Spring 在运行时依据配置创建实例，把另一份服务实现注入其中。框架替程序做了装配，也把装配藏出了普通 Java 的调用链。预处理要用原生 Java 写出**实际装配的结果**，让内核可以从一个静态起点走进原来的业务方法。

假设下单接口的构造器接受 `Pricing`，当前配置注入的是 `RetailPricing`，两者都能在业务源码里找到。下面只列装配和入口，`quote` 的方法体沿用原件。

```diff
-@RestController
 class OrderEndpoint {
     private final Pricing pricing;
     OrderEndpoint(Pricing pricing) { this.pricing = pricing; }

-    @PostMapping("/quote")
-    int quote(@RequestParam("units") int units) { return pricing.quote(units); }
+    int quote(int units) { return pricing.quote(units); }
 }
+
+class Beans {
+    static final OrderEndpoint ORDERS = new OrderEndpoint(new RetailPricing());
+}
```

现在从 `Beans.ORDERS.quote` 就能发起同一次业务调用。静态可达的是**取得接收对象的路径**，`quote` 仍是实例方法，注入的计价逻辑仍要执行。若观察范围从收到原始 HTTP 请求开始，缺参、绑定失败以及原接口怎样响应也在范围内，上面的起点只覆盖成功绑定之后。

为什么许多服务把装配写清就够了？这里借了 Java 服务端一个重要的常识：**通常按无状态服务设计。** 同一个实例可以服务一千次请求，第一千次请求的业务结果却无需知道前九百九十九次在这台 JVM 的堆里留下了什么。长期留存、只影响速度的缓存也符合这个假设。普通对象和缓存代码仍按源码执行。[业务至上](06-业务至上.md)

把一个事实改掉，预处理的责任就跟着变了。假设剩余库存就存在这个服务实例里，上次扣完剩 7 件，这次就只能从 7 件开始算。即使找到了正确的服务方法，每次从构造器的初值开始也会算错。此时必须主动把 `remaining` 标为 `@N.EntryState`：这次读到的原有库存是 E，扣减写回是 S。标记让一次请求结束以后仍有业务意义的写入留在结果里。同一条判断也适用于名叫 cache 的字段：如果命中会省掉一次有业务意义的对外调用，就要保留这个差别。[PERS 中的库存与创单](07-PERS登场.md)

## 前端 · 为什么从状态两头看

到了前端，起点变了。一个页面可以活过许多次点击、请求和渲染。上一次选了哪笔账单，下一次点「支付」就要用它；请求返回时改了哪个金额，下一次渲染就要显示它。**服务端常见的无状态假设，到了页面上恰好反过来：靠内存里的状态把多次调用接起来，本来就是页面的工作方式。** 我们把页面持有、会影响后续业务或展示的这部分状态称为 VO（visual object）。

页面源码又有两种写法混在一起：算法可以写成普通 JS 或 TS，而「何时触发这段算法」「哪个值送到哪个组件属性」常写成框架和模板的绑定。如果只找现成的 JS 函数，就会漏掉绑定本身表达的业务。沿着同一份 VO 可以把两头认出来：**从宿主事件追到应用的 handler，看状态怎样产生或改变，是生产归一化；从界面上一项具体属性反查它怎样从状态取值，是消费归一化。** 两头共享状态的身份，各自有一次独立调用。

## 前端生产 · 把事件还原为应用的一次调用

一次生产从宿主把控制权交给应用开始。按钮上的监听容易认；框架代为注册的生命周期回调，光看函数名就认不出来。要沿实际派发关系找到应用接手的 handler。事件绑定脱糖到这里，内核就可以像调用 `main` 一样调用它。原来由它调用的业务函数，仍在这次调用的范围里。

看一个订单页面的两个绑定。用户点击「加一件」，卡片显示新的数量。这里的 `draft` 属于当前页面实例。

```vue
<template>
  <button @click="addOne">加一件</button>
  <OrderCard id="summary" :units="draft.ready ? draft.units : 0" />
</template>

<script setup lang="ts">
import { reactive } from "vue";

const draft = reactive({ units: 0, ready: false });

function addOne(): void {
    draft.units += 1;
    draft.ready = true;
}
</script>
```

生产归一化从点击真正进入的 `addOne` 开始。模板和响应式容器脱糖后，交出的生产入口如下。模块里的 `draft` 代表刚才那个页面实例，初始化发生在创建实例时。

```typescript
import * as N from "@normalizer/stdlib";

/** @N entryState */
const draft = { units: 0, ready: false };

export function addOne(): void {
    draft.units += 1;
    draft.ready = true;
}
```

假设点击前已经有 4 件，这次就写入 5，再把 `ready` 写成 `true`。单独分析这次点击时，原有数量未知，它来自 E。两次写入按实际顺序进入 S。声明里的初值 0 不能代替点击前的数量。

VO 要由预处理主动标记。一个选中的订单号即使从未显示，只要下次提交还要读取，就要认出它属于哪个页面实例。handler 为了算新数量临时开一个局部变量，也会占用内存，但它的作用随这次计算结束。这就是为什么页面通常有许多 VO 要标，却不能把每一个堆对象都标成 VO。

handler 还可能发 HTTP 或 RPC 请求，或调用宿主的支付接口。这些真实的外部调用都进入 S，回执由发生调用的那一步绑定。成功后写 VO、失败后提示用户，就分别保留在各自路径上。一个事件即使只发出了请求，也值得从它的真实 handler 分析。[PERS 中的外部调用与回执](07-PERS登场.md#pers-01-参数环境和回执的来源)

## 前端消费 · 这一次渲染给属性什么值

为什么还需要消费归一化？即使找齐了所有 handler，知道每个事件怎样改动 VO，也还回答不了用户会看到什么。假设两页都用上面的 `addOne`，只给按钮加一条绑定。一页写 `:disabled="draft.units >= 4"`，另一页写 `:disabled="draft.units > 4"`。连点四次，两份草稿都正好是 4 件，第一张页面的按钮已经不可用，第二张还能点。**生产逻辑相同，界面上的业务规则却可以不同。**

双向绑定让这件事尤其直观。编辑输入框，框架可以替应用把新值写回状态；程序改了状态，框架又替应用算出要填回输入框的值。后一半即使只写成一个模板属性，也是在执行一次取值。沿着这条方向走，到具体实例的具体属性就有了清晰的观察范围，例如某个 `div` 的 `title`，或这里 `OrderCard#summary` 的 `units`。

把该属性的表达式放进一个**同步、无参的取值函数（supplier）**，模板藏起来的那次求值就有了标准函数入口。它绑定原页面实例，实际读到的已有 VO 归 E，交给该属性的值归 R。上例的分析模块因此可以再导出一个函数。

```typescript
/** @N componentProp OrderCard#summary.units */
export function cardUnits(): number {
    return draft.ready ? draft.units : 0;
}
```

单独调用 `cardUnits()` 就能问「此刻给这张卡片多少件？」这次读的是卡片所属实例当时的草稿，无须猜它之前点了几次按钮。事件怎样把页面带到这个状态，由生产入口解释；给定这个状态，属性得到什么值，由消费入口解释。[属性入口的约定](04-AI救赎.md#ai-10-组件属性投影必须同步无参) · [属性入口的完整 PERS](07-PERS登场.md)

## 规则区

**为了把场景映射成标准函数入口，只允许以下改动。**

| 原场景里已经存在的事实 | 允许怎样写进分析副本 |
|---|---|
| 服务框架已经绑定了请求参数，装配了服务实例及依赖 | 把该观察起点已经取得的参数写进入口签名，用原生代码显式给出实际装配，使同一服务方法可直接调用。 |
| 宿主直接或经框架把事件交给应用的 handler | 将这条绑定脱糖，暴露实际接手事件的 handler，保留宿主交给它的实参和接收实例。 |
| 服务实例或页面持有跨调用的业务状态 | 显式标记原有状态。若状态藏在框架容器里，可以把它还原为同一实例持有的原生状态。 |
| 模板在具体实例上为某项属性求值 | 把原取值表达式提成同步无参的 supplier，绑定原实例和属性，保留原来的求值条件。 |

只改表中为建立入口所必需的部分。若同一段代码还涉及库调用或无界循环，须另按相应的预处理规则判断。**没有规则允许的改动，一律禁止。** [AI救赎 · 预处理停在哪儿](04-AI救赎.md#ai-05-预处理停在哪儿)

### SC-01 入口保留原场景的调用起点

HTTP 或 RPC 从约定的服务边界开始，前端生产从宿主直接或经框架转交给应用的回调开始。预处理把触发和实例装配写明，保留从这个起点到完成之间的业务判断、状态和对外动作。

**示例**　按钮绑定 `onSubmit`，处理器先检查能否重复提交，再调 `orders.create`。选 `onSubmit` 为入口，两条路径分别是拦住这次提交和发起创单。若跳到同样可调用的 `orders.create`，就会把本来被拦住的点击也算成创单。

### SC-02 一次消费对应一个实例的一项实际观察

属性入口保留模板上「哪个实例、哪项属性、何时会求值」的对应关系。分析整页生产要找全实际的业务回调，分析整页消费要找全实际的展示和交互属性观察。两侧都由原页的绑定确定范围。

**示例**　若把订单卡片包在 `v-if="visible"` 里，`visible` 为真且 `draft.ready` 为假时，卡片收到 0。若 `visible` 为假，卡片没有挂载，根本没有这次 `units` 求值。两种结果在页面上有清楚的区别。
